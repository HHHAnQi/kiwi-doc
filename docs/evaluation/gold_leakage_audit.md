# Gold Leakage Audit (PR-7f.2c.2 Task 2)

> Scope: `eval/agentic/datasets/agentic_v2.pilot20.jsonl` (legacy pilot).
>
> Method: For every answerable case, compare `gold.goldAnswer` against
> `gold.goldEvidence[].contentSnippet` for:
>  1. Exact match (after whitespace strip)
>  2. Substring containment (either contains the other)
>  3. Bigram-set Jaccard overlap (Chinese-friendly, no tokenization)
>
> Gold20 is omitted from the leakage analysis — by design it has empty
> `referenceAnswer` and `contentSnippet` (template, not annotation).
>
> Read-only. **No dataset rows modified.**

---

## Final verdict: **FAIL — 100% annotation leakage in pilot20**

In **12 of 12** answerable pilot20 cases, the gold answer text is character-for-character
identical to the cited evidence snippet. Any faithfulness/citation metric computed
on this dataset today is structurally the metric "is the answer the same string
as one of the cited chunks" → trivially 1.0 → no information.

## 2. Root cause

`agentic_v2.pilot20.jsonl` was generated in PR-7f.2b.1 by mechanical extraction
from `eval/golden/golden_v2_grounded.jsonl`. That file's `ground_truth_answer`
field was in turn generated by `regen_ground_truth.py` (with `regen_method:
"direct_match"`) — the script **extracted the gold answer by lifting a sentence
from the chunk verbatim**, so by construction the answer == a substring of the chunk.

This is a *data-provenance* bug, not an annotation-mistake bug. Whoever fills the
`FILL_*` markers in pilot20 today would have no choice but to copy the gold answer
into the snippet (since gold answer already came from a chunk sentence) — UNLESS
the annotation guideline forbids it (which it does: see `gold_annotation_guideline.md
§6` and `validate_gold_dataset.py` annotation-leakage check).

---

## 3. Impact on metrics

Any of the following metrics becomes uninformative on pilot20:

| Metric | Why unstable on leakage-100% dataset |
|---|---|
| `faithfulness` (RAGAS / LLM-judge) | The answer IS the cited chunk → grounding trivially proven → metric saturates to ~1.0 |
| `citation_precision` | Cited evidence contains the answer → precision trivially 1.0 |
| `citation_recall` | Same |
| `unsupported_claim_rate` | No unsupported claims possible if answer ⊆ snippet |
| `answer_correctness` vs gold | Same string → token-F1 = 1; tells us nothing |
| `gold_evidence_recall` | Becomes "did the agent retrieve *this specific* chunk" → measures retrieval not generation |

So the metrics framework is fine; the **data fails its purpose**.

---

## 4. Mitigation checklist (for future annotators)

Every recommendation below is enforced by `validate_gold_dataset.py`
(PR-7f.2c.1 Task 3 + this audit confirms it):

- ✅ `contentSnippet` must NOT equal `referenceAnswer` (exact match blocker exists)
- ✅ `contentSnippet` must NOT contain `referenceAnswer` (substring blocker exists)
- ✅ `rationale` must NOT be contained in `referenceAnswer`
- Annotator must write the referenceAnswer **in their own words**, NOT copy from chunk
- Annotator must take `contentSnippet` from a *different region* of the chunk than
  the answer-bearing sentence, OR shorten to non-answer-context

---

## 5. Quantified threshold recommendation (for discussion)

Current leakage guard in `validate_gold_dataset.py` only checks exact / substring
equality. Concretely from this audit:

| Threshold | Effect |
|---|---|
| jaccard > 0.9 → reject | catches 100% of pilot20 leakage |
| jaccard > 0.7 → reject | catches 100% but risks rejecting legitimate "reformatted paraphrase" |
| jaccard > 0.5 → reject | tighter, may over-reject |

**Recommendation**: add jaccard > 0.7 as a WARN in `validate_gold_dataset.py` and
require reviewer signoff on > 0.9 cases. Pure policy, doesn't auto-reject.

(P2 only — the existing exact-match blocker is sufficient to make pilot20 fail
today; the jaccard threshold mainly catches future subtle paraphrases.)
